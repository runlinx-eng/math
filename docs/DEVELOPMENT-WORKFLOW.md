# 数学树长期开发工作流

状态：长期基线。适用于数学探索（数学树）仓库的所有后续开发分支。本文规定如何交付，不替代产品规范，也不直接授权新的产品功能。

## 一、规则入口与权威性

- `AGENTS.md`：Codex/开发代理统一入口；只概述职责、边界和现行文档入口。
- 本文：唯一长期开发流程；不在阶段报告或 PR 中再写一套流程。
- `docs/spatial-learning/INTERACTION-RULES.md`：已合并主线的当前知识地图交互规则。
- `docs/LEARNING-DESIGN.md`：学习设计、学习记录及能力推断的边界。
- `docs/EXECUTION-PLAN.md`：当前阶段计划与未完成事项；不自动覆盖最新用户决策。
- `README.md`：启动、使用说明与维护索引。
- `docs/deployment/vps.md`：静态 VPS 预览、发布、隐私边界与回滚说明。
- `docs/VALIDATION.md`：技术验证与实际使用验收的证据和局限。
- 新增领域规范（例如文字术语）只有合并主线后才成为对应领域的正式规范。待合并分支只约束该分支自身的改动。

当内容冲突时：本次用户明确确认的目标与变更边界 > 主线当前有效的领域产品规范 > 历史实验/验证记录。技术数据事实以可追溯的源数据和实际实现为准；不能仅凭文档虚构数学关系。用户尚未批准的候选方案不当作现行规则。历史资料仍可查，但不是执行指令。

## 二、每个任务的六步闭环

1. **确认目标与规则**：先核对当前 main、在做的分支、相关现行规范。用简短说明确定目标、不可改变的边界与可观察的验收标准。已有明确授权直接推进，不再增加审批。
2. **独立分支开发**：从合适的最新 main 创建任务分支。不得顺手修改其他未完分支、无关功能、数学源数据或用户记录。影响较大时先最小试验，再扩大。
3. **同步规则、文档与测试**：如有正式行为/名称变更，同一 PR 更新相关规范、产品实现、测试预期；旧断言必须依据明确的新规则修订，不为通过 CI 而削弱正确检查。纯内部修改不强制更新产品文档。
4. **自动验证**：执行受影响测试；GitHub Actions 对所有 PR 运行基础检查，对界面/交互相关更改运行隔离 Chromium 浏览器检查。失败先归因，处理后在最新提交重新验证；不能把旧 SHA 的成功视为新 SHA 的通过。
5. **验收与风险判定**：提供改动前后差异、可复现操作或在线预览、适用 CI 结果与已知限制。普通、范围明确且无阻塞风险的 PR 可以依据用户给予的常设授权直接工程收尾，无需逐 PR 重复申请；用户明确反馈「本阶段验收通过」等同于该阶段正常范围内的产品验收与合并认可。仍将未完成的触控、儿童教学、视觉精修等人工验收单独记录，不能由 CI 冒充。
6. **Git 收尾**：按下方常设授权分类。普通 PR 在最新 HEAD 的适用 CI、依赖、兼容性和数据安全检查通过且无阻塞问题时，由当前执行开发的代理直接合并 main，不重复请求授权；高风险变更必须另外取得明确许可。合并前核对主线与依赖、合并后核对 main 的必要回归和遗留问题。**合并与 VPS 发布分开授权。**

用户只需要决定产品取舍、变更范围与最终是否接受；普通实现、测试和文档同步由开发代理自行完成。

### 合并的常设授权（用户 2026-11-12 确认）

本节取代旧阶段报告中「任何 PR 都要单次合并授权」的通用说法；旧任务在当时尚未被授权的历史记录仍保留为历史事实。

- **常规 PR 可直接合并**：已确认目标范围内的功能开发、界面交互与视觉改良、无损 Bug 修复、测试与文档、非破坏性重构，在必要证据齐备后，由当前执行的开发代理直接合并，不需要用户重复说「授权合并」。若用户明确表示某一阶段「验收通过」，这同时认可该阶段正常范围内的工程收尾与合并，不能据此自动扩大到无关 PR。
- **合并前的硬门槛**：重新核对 `main` 与 PR 最新 HEAD、目标分支、依赖和文件差异；最终 HEAD 上 `required-checks` 必须成功，Overview、P8 等**实际适用/触发**的工作流也必须成功；涉及学习、离线、备份、历史、Service Worker 或记录的，运行相应 P7/P9/P10 数据安全与兼容回归。存在失败、取消、未完成、红色检查、实际交互阻塞、冲突、数据风险或证据不足时不合并；不得跳过、强制点击、削弱断言或用旧 SHA 绿灯替代。记录验收边界和未完人工事项。
- **高风险变更每次单独授权**：删除/替代核心能力或无法证明等效路径，修改数学源节点/真实关系/判题与学习任务语义，改变学习记录格式、存储迁移/合并/清理与旧备份兼容、可能损失学习数据的操作，重要安全/权限/账号与外部服务变更，重大架构方向改变，及无法确认影响范围的改动；即使 CI 通过也需用户明确决定后才能合并。界面入口去重若已证明功能保留、历史恢复不受影响，可按普通改动处理；证据不全则属于高风险。
- **产品验收与工程合并区分**：用户的阶段认可允许对应正常范围合并，非阻塞的字体、动画、视觉风格及独立儿童实测可列为后续迭代；但核心节点不能点击、学习现场丢失、备份损坏、真实功能不可达等阻塞问题不得延期掩盖。提交和合并记录应如实注明 `manualVerified` 的实际范围。
- **发布须另行授权**：任何 PR 合并或主线 CI 成功均不授予 VPS 部署、正式上线或回滚许可。当前 `.github/workflows/deploy-vps.yml` 是仅 `workflow_dispatch` 的手动部署，须对 **main** 运行并确认 `confirm_deploy=true`；回滚也只能按用户针对该次操作的明确指示执行。不得为了加速合并更改这一发布隔离。
- **执行含义**：「自动合并」指开发代理在本次执行中验收合格即可主动执行合并，**不表示 GitHub CI 在后台自动合并**；仓库 GitHub 原生 `allow_auto_merge` 是否启用属于另一项设置。没有正在执行的代理/合并任务时，不承诺后台自动完成。合并后查看最新 `main` SHA 和必要回归；下一阶段从已验证的主线建立独立分支。

## 三、什么变化需要同步

| 变更类型 | 同步对象 |
| --- | --- |
| 地图交互、导览、文案名称等产品规则 | 现行领域规范 + 对应实现 + 相关断言/浏览器场景 + 用户验收说明 |
| 知识关系、数学内容、年级归属、学习记录 | 真实来源或映射依据 + 实现 + 数据与兼容测试 + 必要的数学审阅范围 |
| 部署、缓存、运行环境 | 配置/部署说明 + 发布或回滚检查 + 相关测试；不必改无关数学规则 |
| 纯重构或性能修复 | 实现 + 受影响回归；规则未变时不新增文档 |
| 验证方法变化 | 测试和 CI + 简短理由；不得暗中改变已有产品行为 |

优先改已有规范，不为每个阶段、修复或 PR 新增治理文件。正式规则写“现在应怎样”，历史记录写“当时发生过什么”，二者不可混作一个验收标准。

## 四、CI 失败归因（必须先判断再修复）

1. **代码缺陷**：当前正式规则要求的真实行为未满足。修代码，保留有效测试。
2. **旧测试/旧预期**：真实行为符合用户确认的新规则，但断言仍要求废弃设计。更新断言与依据，并保留不变的行为回归。
3. **验证方法问题**：固定等待时间、选择器、截图时机、浏览器环境、缓存/状态污染导致检查不能可靠反映结果。修复验证手段，确认状态稳定并重测。
4. **尚不确定**：证据不足时保持失败状态，报告可复现步骤与未排除原因，不归咎代码或测试，更不得删除断言求绿灯。

优先以真实界面状态、数据事实和当前规范交叉核对，不能仅以像素数量/动画单帧做永久业务断言。固定版本环境与隔离浏览器存储。失败修复必须在变更后最新提交上重新跑。

## 五、分支、PR 与完成条件

- main 是正式集成基线；一个任务一个分支，名称按 feat/、fix/、chore/ 区分，默认经 PR 合并。
- PR 说明只需：目标及不变项、必要规则同步、执行的测试与结果、需要用户确认的地方。直接用 PR 作为当次验收记录，不另写审批书。
- **工程合并与产品验收分离**：普通 PR 已有长期合并授权，无需逐次申请；最新必要 CI 与兼容性检查通过后可合并，并将未完成的非阻塞视觉/交互/教学问题继续留在对应 Issue。高风险 PR 仍需单次明确授权；CI 通过不等于产品或教学效果验收。
- 对已合并改动，去掉现行文档中的“候选、待合并”等过期状态，避免下一轮把历史分支当权威。
- 保护未完成的文字优化等并行分支；后合并者先吸收 main 的工作流/CI 更改，再运行最新完整回归，不能用旧 CI 文件覆盖基线。

### GitHub 默认使用本地 CLI（用户 2026-11-14 确认）

- 本项目后续对话默认使用本地 GitHub CLI `gh` 操作 GitHub，包括 Issue、PR、检查状态和已授权的合并；Git 提交与推送仍用 `git`。不默认走需要逐次弹窗的 GitHub 插件或网页。此项是用户明确的工具偏好。
- 已授权范围内的常规操作连续执行，无需用户守候批准。运行前核对 `gh api user --jq .login`、目标仓库与所需权限；本项目目标为 `runlinx-eng/math`，命令显式指定 `--repo runlinx-eng/math`（API 路径也明确仓库）。沿用有效登录，不读取或输出明文令牌。
- 非交互运行设置 `GH_PROMPT_DISABLED=1`、`GIT_TERMINAL_PROMPT=0`、`GH_PAGER=cat`，必要时设置 `GH_EDITOR=false`、`GH_BROWSER=false`；提供完整标题、正文、合并方式等参数，多行正文通过临时文件与 `--body-file` 传入。标准输入关闭、不分配交互终端，并为命令设置合理超时；长时间 CI 等待分段检查并报告状态。
- 写入后回读目标对象，验证内容、状态与提交 SHA。失败或超时先检查是否已产生远端结果，避免重复创建；登录失效、权限不足或平台明确拒绝时报告具体阻塞，不循环等待输入，不自动改换身份或提升权限。
- 本规则选择执行渠道，不扩大任务授权，不绕过明确的访问限制、分支保护或审批拒绝。普通 PR 仍须满足本文件的 CI、依赖与兼容检查；高风险变更、VPS 部署和回滚仍按原有要求另行授权。没有运行中的代理或任务时，不承诺后台自动处理。
- 已有验证：2026-11-14 使用现有 `runlinx-eng` 登录，在无控制终端、标准输入关闭、提示禁用的独立进程中完成 Issue 创建、标题/正文更新、关闭及逐步回读，全部命令成功；[测试 Issue #110](https://github.com/runlinx-eng/math/issues/110) 已关闭。该证据覆盖 Issue 操作，不能替代后续 PR 合并或部署的实际验证。

### CI 与 main 分支保护

- `.github/workflows/pull-request-baseline.yml` 是 PR 的固定检查入口。每个 PR 都会产生同一个稳定检查项：`required-checks`。
- `static-checks` 每次运行运行时模块语法检查、当前稳定的数学关系/全景/过滤/部署测试，以及部署脚本语法检查；文字分支新增的术语、名称、导航和关系表达测试在对应文件存在时也纳入。涉及 `dist/`、清单中的浏览器脚本、CI 分组 helper/测试、交互规范或 `docs/language/` 时，在独立 runner 的固定浏览器分组中运行 Chromium，由同名 `required-checks` 最终汇总。
- 浏览器清单与执行规则只在 `scripts/required-browser-checks.mjs` 维护。当前分为界面、既有数学证据、数位证据、家族扩展一、家族扩展二、P10、P8 性能七组；组内串行，组间 `fail-fast: false`。扩展一检查成熟扩展、数轴路径与分数排序；扩展二检查分组、几何变换与角度记录的双视口真实操作。PR #146 的四条扩展命令实测合计 19 分 57 秒；新增变换时拆分既有矩阵，不减少、重复或跳过任何命令与产物，不提高 35 分钟限时。P8 trail 的 baseline 与正常模式在同一个专用 runner 顺序执行；P10 保留升级重复验收、独立重试、备份和完整课程测试。新增或调整组时同步工作流矩阵与清单覆盖测试，不遗漏原有脚本或断言。
- PR 范围明确不相关时，每组仍留下显式“不适用”结果，不宣称执行过浏览器。范围输出缺失、非法或分组缺失均不得放行。`push main` 与手动运行始终执行完整浏览器回归。浏览器测试通过真实页面状态验证，不用固定等待代替状态判断。
- `required-checks` 始终汇总，要求静态检查、全部浏览器分组和每条适用命令成功；失败、取消、跳过、未知或缺失结果都不能成为绿灯。每组分别上传截图与小型执行记录，记录当前 SHA、工作流运行和尝试编号；只接纳同一运行、同一 SHA 下该组最新的可用记录。重跑失败作业时，如此前成功组的记录无法取得，应重跑整个工作流，不得缺证据放行。Node 审计与覆盖资料保留在独立 Artifact 中。
- 不要直接用 `tests/*.test.mjs` 把仓库全部历史测试纳入阻塞门禁。2026-11-02 的一次全量诊断为 1,073 项中 1,065 项通过、8 项失败：内容计划的 `dist/exploration.js` 输入指纹未同步；关系使用审阅因 `dist/learning/learn.js` 指纹变化而要求重新审阅；旧坐标测试用精确浮点相等，和验证记录中 1e-9 容差的做法不一致；旧导览测试对第一步点击后的 ready 状态与当前实现不一致。它们不是本次 CI 修改引起的故障，也不能靠删除断言或自动刷新审阅指纹处理。应分别确认来源、现行规则和验证方法后，再决定修实现、更新旧预期或调整检查方法。

- GitHub 的 main 分支保护只要求 `required-checks` 通过；不要把仅在特定文件变化时才出现的独立工作流/任务设为必需检查，否则无关 PR 可能一直等不到该检查。
- main 应要求通过 PR 合并、禁止强制推送和删除；当前单人开发不要求第二人审批。分支保护是 GitHub 仓库设置，不是代码文件；在检查项稳定并合入 main 后一次性启用。

## 六、发布与代码合并的区别

- **合并 main 不会自动更新 VPS 预览站**：`Pull request required checks` 对 `push main` 仍跑完整 Node、Chromium 和兼容回归，但成功不会触发部署。`.github/workflows/deploy-vps.yml` 当前仅支持用户单独授权后的手动 `workflow_dispatch`（main、`confirm_deploy=true`）。代码合并不等于公开预览或生产发布。
- 部署任务先核对 `RELEASE_SHA` 与远程当前 `main` 一致，过期发布会跳过；只有取得用户对该次发布的明确授权后才允许运行手动部署工作流。PR、main push、手动运行测试、CI 成功或失败都不能自行触发 VPS 发布；并发提交的旧版本不得覆盖新主线。
- 手动发布（`main` + `confirm_deploy=true`）、原子版本切换、失败时恢复上一版本，以及 **需单独授权的手动回滚** 均保留；部署和回滚串行执行。不修改 VPS 443/Xray、认证服务与端口布局。
- 当前已明确批准将 P1–P6-B 的 CI 通过成果先整合到 main，后续 UI 和儿童体验改进继续在新的主线分支实施。合并不构成对尚未完成的人工视觉、50 个数学思维节点教研或实际教学效果的验收。
- 合并多条堆叠 PR 时，只在明确可发布的完整集成状态更新 `main`，避免将工程中间版本暴露到预览站。

## 七、当前任务与后续项目边界

当前文字概念优化在独立分支验收后合并；本次工作流任务独立从 main 出发，先完成规则/CI 闭环，不动产品功能。下一个云端部署任务单独立分支，先争取只读在线预览和可回滚发布；在未另行确认前，不添加账号、服务端学习记录、云同步或外部追踪。此后小学 1–6 年级分布/排列作为新的知识查看维度，需先有课程来源与映射说明；不能以年级顺序取代或删除真实数学前置关系，也不预先改动 3D 基准坐标。

## 八、本工作流基线自身的验收

- AGENTS 只有清楚的正式入口；历史 AGENTS 内容可追溯且标明失效。
- 当前交互规范不再写过期的“候选分支待合并”结论。
- 每个 PR（包括仅改文档/规则）都会产生固定的 `required-checks`；相关产品界面/交互变化触发独立 runner 的真实 Chromium 分组回归，最后由这个稳定检查项汇总，报告对应最新提交。
- 能依据一个明确例子分别解释代码缺陷、旧断言和测试时机问题。
- 一次真实 PR 经过“变更—同步—自动验证—依据常设授权分类/必要时专门审批—合并—检查主线”；尚未解决的视觉或教学体验验收须独立记录，不能冒充已完成。
